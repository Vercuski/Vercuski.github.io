Software Design Patterns & Anti Patterns

A catalog of classic design patterns grouped as creational, structural, behavioral and concurrency, followed by named anti-patterns: generic, object-oriented, programming, methodological, configuration management and architecture.


TL;DR

A lookup table of classic design patterns grouped as creational, structural, behavioral and concurrency, followed by named anti-patterns. Each name links to its own note (problem, solution, structure, when to use, trade-offs); pattern notes live in Design Patterns/Classic Patterns and anti-pattern notes in Design Patterns/Anti-Patterns. The Pattern Catalog lists them all by category. Distributed-systems patterns are in Distributed Systems Pattern Catalog; architecture styles are in Architecture Styles Compared.

Enterprise application patterns

Distributed-systems patterns (API Gateway, Circuit Breaker, CQRS, Event Sourcing, Outbox, Retry, Saga) live in Distributed Systems Pattern Catalog; cache-aside lives in Caching Patterns.

NameDescription
Entity Component SystemEntities are composed of data components, and systems operate on entities that have particular components. Most associated with game development for representing game-world objects.
Pipeline PatternExecutes cross-cutting concerns such as validation and logging before or after handlers.
Repository PatternEncapsulates data access and keeps business logic independent of persistence. With EF Core, DbContext and DbSet already play this role; see 7 .NET Habits to Reconsider.

Creational

A creational pattern creates objects.

NameDescription
Abstract FactoryProvide an interface for creating families of related or dependent objects without specifying their concrete classes.
Example: GUI Factory
Builder PatternSeparate the construction of a complex object from its representation, allowing the same construction process to create various representations.
Example: StringBuilder
Dependency InjectionA class accepts the objects it requires from an injector instead of creating the objects directly.
Factory MethodDefine an interface for creating a single object, but let subclasses decide which class to instantiate. Factory Method lets a class defer instantiation to subclasses.
Example: Shape Factory
Lazy InitializationTactic of delaying the creation of an object, the calculation of a value, or some other expensive process until the first time it is needed. This pattern appears in the GoF catalog as "virtual proxy", an implementation strategy for the Proxy pattern.
Multiton PatternEnsure a class has only named instances, and provide a global point of access to them.
Object PoolAvoid expensive acquisition and release of resources by recycling objects that are no longer in use. Can be considered a generalisation of connection pool and thread pool patterns.
Prototype PatternSpecify the kinds of objects to create using a prototypical instance, and create new objects from the 'skeleton' of an existing object, thus boosting performance and keeping memory footprints to a minimum.
Example: Object.clone()
Resource Acquisition Is InitializationEnsure that resources are properly released by tying them to the lifespan of suitable objects.
Singleton PatternEnsure a class has only one instance, and provide a global point of access to it.
Example: Logger

Structural

A structural pattern organizes classes and objects to form larger structures that provide new functionality.

NameDescription
Adapter PatternConvert the interface of a class into another interface clients expect. An adapter lets classes work together that could not otherwise because of incompatible interfaces. The enterprise integration pattern equivalent is the translator.
Example: SocketAdapter
Bridge PatternDecouple an abstraction from its implementation allowing the two to vary independently.
Example: JDBC Driver
Composite PatternCompose objects into tree structures to represent part-whole hierarchies. Composite lets clients treat individual objects and compositions of objects uniformly.
Example: File System
Decorator PatternAttach additional responsibilities to an object dynamically keeping the same interface. Decorators provide a flexible alternative to subclassing for extending functionality.
Example: I/O Streams
Delegation PatternExtend a class by composition instead of subclassing. The object handles a request by delegating to a second object (the delegate)
Extension ObjectAdding functionality to a hierarchy without changing the hierarchy.
Facade PatternProvide a unified interface to a set of interfaces in a subsystem. Facade defines a higher-level interface that makes the subsystem easier to use.
Example: JDBC Template
Flyweight PatternUse sharing to support large numbers of similar objects efficiently.
Example: Character Cache
Front ControllerThe pattern relates to the design of Web applications. It provides a centralized entry point for handling requests.
Marker InterfaceEmpty interface to associate metadata with a class.
Module PatternGroup several related elements, such as classes, singletons, methods, globally used, into a single conceptual entity.
Proxy PatternProvide a surrogate or placeholder for another object to control access to it.
Example: Virtual Proxy
Twin PatternTwin allows modeling of multiple inheritance in programming languages that do not support this feature.

Behavioral

A behavioral pattern describes collaboration between objects.

NameDescription
Blackboard PatternArtificial intelligence pattern for combining disparate sources of data (see blackboard system)
Chain of ResponsibilityAvoid coupling the sender of a request to its receiver by giving more than one object a chance to handle the request. Chain the receiving objects and pass the request along the chain until an object handles it.
Example: Filter Chain
Command PatternEncapsulate a request as an object, thereby allowing for the parameterization of clients with different requests, and the queuing or logging of requests. It also allows for the support of undoable operations.
Example: Runnable
Fluent InterfaceDesign an API to be method chained so that it reads like a DSL. Each method call returns a context through which the next logical method call(s) are made available.
Interpreter PatternGiven a language, define a representation for its grammar along with an interpreter that uses the representation to interpret sentences in the language.
Example: SQL Parser
Iterator PatternProvide a way to access the elements of an aggregate object sequentially without exposing its underlying representation.
Example: Iterator, List Iterator
Mediator PatternDefine an object that encapsulates how a set of objects interact. Mediator promotes loose coupling by keeping objects from referring to each other explicitly, and it allows their interaction to vary independently.
Example: Chat Room
Memento PatternWithout violating encapsulation, capture and externalize an object's internal state allowing the object to be restored to this state later.
Example: Undo Mechanism
Null ObjectAvoid null references by providing a default object.
Observer PatternDefine a one-to-many dependency between objects where a state change in one object results in all its dependents being notified and updated automatically.
Example: Event Listeners
Result PatternReturn explicit success or failure instead of relying on exceptions for expected failures.
Servant PatternDefine common functionality for a group of classes. The servant pattern is also frequently called helper class or utility class implementation for a given set of classes. The helper classes generally have no objects hence they have all static methods that act upon different kinds of class objects.
Specification PatternRecombinable business logic in a Boolean fashion.
State PatternAllow an object to alter its behavior when its internal state changes. The object will appear to change its class.
Example: ATM States
Strategy PatternDefine a family of algorithms, encapsulate each one, and make them interchangeable. Strategy lets the algorithm vary independently from clients that use it.
Example: Payment Methods
Template MethodDefine the skeleton of an algorithm in an operation, deferring some steps to subclasses. Template method lets subclasses redefine certain steps of an algorithm without changing the algorithm's structure.
Example: AbstractClass.execute()
Visitor PatternRepresent an operation to be performed on instances of a set of classes. Visitor lets a new operation be defined without changing the classes of the elements on which it operates.
Example: Document Export

Concurrency

A concurrency pattern supports concurrent processing.

NameDescription
Active ObjectDecouples method execution from method invocation that reside in their own thread of control. The goal is to introduce concurrency, by using asynchronous method invocation and a scheduler") for handling requests.
Balking PatternOnly execute an action on an object when the object is in a particular state.
Binding PropertiesCombining multiple observers to force properties in different objects to be synchronized or coordinated in some way.
Compute KernelThe same calculation many times in parallel, differing by integer parameters used with non-branching pointer math into shared arrays, such as GPU-optimized Matrix multiplication or Convolutional neural network.
CPU Atomic Operationx86 and other CPU architectures support a range of atomic instructions that guarantee memory safety for modifying and accessing primitive values (integers). For example, two threads may both increment a counter safely. These capabilities can also be used to implement the mechanisms for other concurrency patterns as above. The C#") language uses the Interlocked class for these capabilities.
Double-Checked LockingReduce the overhead of acquiring a lock by first testing the locking criterion (the 'lock hint') in an unsafe manner; only if that succeeds does the actual locking logic proceed.

Can be unsafe when implemented in some language/hardware combinations. It can therefore sometimes be considered an anti-pattern.
Event-Based Asynchronous PatternAddresses problems with the asynchronous pattern that occur in multithreaded programs.
Guarded SuspensionManages operations that require both a lock to be acquired and a precondition to be satisfied before the operation can be executed.
Join PatternJoin-pattern provides a way to write concurrent, parallel and distributed programs by message passing. Compared to the use of threads and locks, this is a high-level programming model.
Lock PatternOne thread puts a "lock" on a resource, preventing other threads from accessing or modifying it.
Messaging Design PatternAllows the interchange of information (i.e. messages) between components and applications.
Monitor ObjectAn object whose methods are subject to mutual exclusion, thus preventing multiple objects from erroneously trying to use it at the same time.
Reactor PatternA reactor object provides an asynchronous interface to resources that must be handled synchronously.
Read-Write LockAllows concurrent read access to an object, but requires exclusive access for write operations. An underlying semaphore might be used for writing, and a Copy-on-write mechanism may or may not be used.
Safe Concurrency with Exclusive OwnershipAvoiding the need for runtime concurrent mechanisms, because exclusive ownership can be proven. This is a notable capability of the Rust language, but compile-time checking isn't the only means, a programmer will often manually design such patterns into code - omitting the use of locking mechanism because the programmer assesses that a given variable is never going to be concurrently accessed.
Scheduler PatternExplicitly control when threads may execute single-threaded code.
Service Handler PatternFor each request, a server spawns a dedicated client handler to handle a request. Also referred to as thread-per-session.
Thread PoolA number of threads are created to perform a number of tasks, which are usually organized in a queue. Typically, there are many more tasks than threads. Can be considered a special case of the object pool pattern.
Thread-Specific StorageStatic or "global" memory local to a thread.

Anti Patterns

Generic

NameDescription
Abstraction InversionUsers need functions implemented within an object but not exposed by the interface.
Ambiguous ViewpointLack of clarity during software design
Big Ball of MudA software system that lacks a perceivable architecture. Although undesirable from a software engineering point of view, such systems are common in practice due to business pressures, developer turnover and software entropy.
Database-as-IPCMisusing databases for temporary messages
Inner-Platform EffectTendency of software architects to replicate their development platform
Input KludgeCode fails to properly validate or sanitize user input, handling it in an ad-hoc/inconsistent manner.
Interface BloatOverload of elements on an interface
Magic PushbuttonUser interface and business logic coupled through a single button click.
Race HazardWhen a system's behavior depends on timing of uncontrollable events
Stovepipe SystemIsolated IT system. For the architecture version, see Stovepipe Architecture Anti-Pattern.

Object-oriented

NameDescription
Anemic Domain ModelDomain objects hold data but no behavior; the business logic lives in separate service classes.
Call SuperA subclass override is required to call the base-class method for the code to work.
Circle-Ellipse ProblemA subtype that can't honor all of its supertype's behavior (a circle can't stretch like an ellipse), breaking substitutability.
Circular DependencyTwo or more modules depend on each other directly or indirectly, so neither can change or be reused alone.
Constant InterfaceAn interface used only to hold constants, leaking implementation details into every implementing class.
God ObjectA single class handles all control in a program rather than control being distributed across multiple classes.
Object CesspoolReusing pooled objects whose state wasn't reset, so later callers get stale data.
Object OrgyAllowing excessive access to object data
Poltergeist Anti-PatternEphemeral controller classes that only exist to invoke other methods on classes.
Sequential CouplingA class whose methods must be called in a particular order to work.
Yo-Yo ProblemAn inheritance hierarchy so deep and fragmented that you keep jumping between classes to follow the logic.

Programming

NameDescription
Accidental Complexity Anti-PatternComplexity the solution introduces that the problem doesn't require.
Action at a DistanceBehavior in one part of a program changes unexpectedly because of an operation somewhere else (often shared mutable state).
Boat AnchorCode or components kept in the system although they serve no current purpose.
Busy WaitingContinuously checking a condition in computing
Caching FailureCache used to remember failed or missing responses
Cargo Cult ProgrammingRitual inclusion of computer code that serves no purpose
Coding by ExceptionAdding a special-case branch for every new requirement instead of generalizing the design.
Error HidingFailing to report details of an error
Hard CodingPutting data in the source code of a program
Lasagna CodeSo many thin layers that a simple change has to pass through all of them.
Lava FlowDead or obsolete code nobody dares to remove, which hardens into the codebase.
Loop-Switch SequenceA loop containing a switch that runs each case in order, encoding a plain sequence of steps as a loop.
Magic NumberA literal value with an important yet unexplained meaning which could be replaced with a named constant.
Magic StringsUnexplained string literals used as identifiers or to drive behavior instead of named constants or enums.
Repeating YourselfDuplicating the same knowledge or logic in several places (violates DRY).
Shooting the MessengerMetaphor referring to blaming the carrier of unwelcome information
Shotgun SurgeryOne change requires many small edits across many classes.
Soft CodingMoving so much logic into configuration that the configuration becomes an unmaintainable program.
Spaghetti CodeSoftware source code with poor structure

Methodological

NameDescription
Copy and Paste ProgrammingDuplicating code instead of creating a reusable abstraction.
Golden HammerApplying a familiar tool or technology to every problem, whether or not it fits.
Invented HereRejecting anything built in-house in favor of external products, even when in-house is the better fit.
Not Invented HereRejecting external solutions and rebuilding them in-house.
Premature OptimizationOptimizing before measuring, trading clarity for speed that may not matter.
Programming by PermutationChanging code by trial and error until it seems to work, without understanding why.
Reinventing the Square WheelIdiomatic expression, meaning to waste effort on something that has already been achieved.
Silver Bullet Anti-PatternExpecting one tool, technique or process to solve a fundamental difficulty.
Tester-Driven DevelopmentA project whose new requirements come mainly from bug reports.
