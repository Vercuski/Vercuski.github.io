Interface Control Document — Tapline ↔ Northgate Payments (ICD-001)

What this ICD fixes

How Tapline and Northgate exchange card data, tokens, charges, results, settlement and disputes. It is a schedule to the Northgate Transit Acquiring Agreement (signed 2026-08-14). Where this ICD and the agreement conflict, the agreement wins. Changes follow §6; neither party changes this interface unilaterally.

1. Parties

SystemOwning TeamContact
Tapline (Confluence Regional Transit)Money Team, CRTHannah Cole, Money Team lead — interface owner; CRT Revenue Operations — settlement and disputes; Tapline on-call (Money) via CRT NOC, 24/7
Northgate Transit Gateway (Northgate Payments)Northgate Transit SolutionsTransit Integration Manager — interface owner; Northgate Merchant Support — settlement and disputes; Northgate Technical Operations, 24/7

2. Interface Description

The interface has eight interface points (IF). Northgate is the merchant acquirer and processor. CRT is the merchant of record (merchant category code 4111, transit).

IFNameProtocolDirectionFrequency/Trigger
IF-1Card verification and tokenizationREST/JSON over HTTPS, mutual TLS + OAuth 2.0 client credentialsTapline → NorthgateReal time, on the first tap of a media token not yet known
IF-2Nightly charge fileSFTP, JSON Lines, PGP-encrypted and signedTapline → NorthgateDaily, delivered by 04:00 local
IF-3Charge resultsHTTPS webhook (HMAC-SHA256 signed, mutual TLS) with pull API GET /v2/charges/{chargeId}Northgate → TaplineAs each charge is processed, by 05:00
IF-4Immediate charge (debt recovery, adjustments)REST, as IF-1Tapline → NorthgateOn demand, when a rider pays a debt
IF-5Card-not-present payments (top-ups, autoload)Northgate Hosted Payment Fields (iframe/SDK) in the app and portal; tokens returned to TaplineRider device → Northgate; Northgate → TaplineOn demand
IF-6Settlement fileSFTP, CSV (Northgate standard v4), PGP-encryptedNorthgate → TaplineDaily, delivered by 05:30 local
IF-7Disputes and chargebacksHTTPS webhook; evidence upload via RESTBidirectionalAs raised; response within network deadlines
IF-8Account updater (reissued cards)SFTP, CSVNorthgate → TaplineDaily, by 02:00 local

Card-data boundary. Validators use Northgate-validated P2PE readers. Encrypted card data travels from the validator through Tapline to IF-1 without decryption. Tapline holds the media token and the payment token only, never card numbers (ADR-0005). In the app and portal, card entry happens inside Northgate's hosted fields (IF-5), so card data never reaches CRT systems.

Transit aggregation. Fares for one card in one service day are combined into a single charge (IF-2). Northgate is responsible for applying card-network transit rules (mass transit transaction rules, including aggregation limits and first-ride risk handling) and will tell CRT in advance of any rule change that affects Tapline (§6).

4. Error Handling & Retry

IFErrorHandling
IF-1Timeout (> 5 s) or 5xxTapline retries with the same requestId and exponential backoff for up to 24 h. Taps are rated meanwhile; the charge waits for the token. After 24 h the medium is treated as declined.
IF-1429 throttledTapline honors Retry-After. Agreed rate limit: 50 requests/s sustained, 150/s burst.
IF-2File rejected (bad trailer or signature)Northgate sends a rejection notice within 15 min. Tapline corrects and re-sends; duplicate charge IDs are ignored. If not resolved by 04:30, both sides' on-call engineers start a bridge call.
IF-2Individual record rejectedReported in IF-3 with status declined and code R0xx (format error). It doesn't block the rest of the file.
IF-3Webhook not deliveredNorthgate retries for 24 h (1, 5, 15, 60 min, then hourly). Tapline pulls any result still missing at 05:00 through the pull API.
IF-3DeclinedTapline raises a debt and adds the token to the deny list. If retryable is true, IF-4 is tried once after 72 h.
IF-6Late (after 05:30)Tapline holds reconciliation and logs an SLA breach; Northgate notifies CRT Revenue Operations with an expected time.
IF-6Totals don't match IF-3Both parties' reconciliation teams investigate the same business day. Neither side adjusts automatically.
IF-7Dispute raisedTapline responds with tap evidence (times, locations, validator IDs), with no rider personal data beyond what the network requires, within the deadline in the notice.

All webhooks are verified by HMAC signature and timestamp; payloads older than 5 minutes are rejected as replays.

5. SLA

  • Availability:
    • IF-1, IF-3 pull API, IF-4: 99.95% monthly, excluding agreed maintenance.
    • SFTP endpoints: 99.9%.
    • Maintenance windows must be agreed 14 days ahead and never fall between 02:30 and 06:30 local time.
  • Latency:
    • IF-1 verification: p95 ≤ 1.5 s, p99 ≤ 3 s.
    • IF-4 immediate charge: p95 ≤ 2 s.
    • IF-3: all results for a file delivered by 05:00 if the file arrived by 04:00.
    • IF-6: settlement file delivered by 05:30.
    • IF-8: account updater file by 02:00.
  • Throughput:
    • IF-1: 50 requests/s sustained, 150/s burst.
    • IF-2: up to 250,000 charges per file. Typical: ~110,000.
  • Support: P1 (charge file rejected, settlement missing, API down) — response in 15 min, 24/7. P2 — response in 2 h. P3 — next business day.
  • Service credits for SLA breaches are set out in the Transit Acquiring Agreement, Schedule C.
  • Reporting: Northgate provides a monthly SLA report. Tapline monitors IF-1 latency and file timeliness independently and compares them with it.

6. Change Management

Change typeNoticeProcess
Breaking change (field removed or retyped, protocol, authentication)90 days written noticeProposed through the Joint Change Board; new version runs in parallel with the old for at least 60 days; certification re-test
Additive change (new optional field, new decline code)30 daysNotice to interface owners; Tapline ignores unknown fields
Card-network rule change affecting transit aggregationAs soon as Northgate is notified, normally ≥ 90 days before effectJoint impact assessment; may need a fare-policy or Tapline change
Emergency security change (e.g. key compromise, TLS policy)72 hours, or less if required by law or the networksCISO and Northgate security lead agree; review afterwards
Certificate and key rotation30 days; overlap period of 14 daysScheduled; both certificates accepted during overlap
  • Joint Change Board: monthly, attended by both interface owners plus CRT Revenue Operations and Northgate Merchant Support. Decisions are minuted, and this ICD is re-issued with a new version when the interface changes.
  • Environments: Northgate provides a certification environment matching production behavior, including test cards for every decline code. Tapline's hardware lab is connected to it permanently.
  • Certification: any change to IF-1, IF-2, IF-4 or the P2PE configuration needs a Northgate certification run before production. Test cases are tagged TC-CERT-xxx in the Test Strategy.
  • Versioning: IF-1/3/4 use URI versioning (/v2/). File formats carry a version in the header. Tapline's adapter code is the only place Northgate formats appear (Integration Architecture §2).
