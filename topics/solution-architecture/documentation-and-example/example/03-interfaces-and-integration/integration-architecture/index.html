Integration Architecture — Project Tapline

Integration rules in one list
  1. Inside Tapline, contexts talk through events, not shared databases. Synchronous calls between contexts are allowed only for reads, and never on the tap path.
  2. Every external system sits behind an anti-corruption layer owned by one context. No external model leaks into the domain.
  3. Every message has a unique ID and every consumer is idempotent. Delivery is at-least-once everywhere.
  4. Contracts are machine-readable and versioned: OpenAPI for REST, AsyncAPI and JSON Schema for events. See the API Specification Guide.

1. Integration Overview

Loading diagram…

The Payments Service connects to Northgate directly, and the Device Management Service to Vantor, rather than through the Integration Service. Those two integrations are central to their contexts and are governed by the card-data zone and edge security rules respectively. Every other external system goes through the Integration Service.

2. Integration Patterns Used

PatternWhereWhy
Store-and-forwardValidators → Device GatewayBoarding must not depend on the network (NFR-AVAIL-03). The validator owns each tap until the cloud acknowledges a durable write.
Event streaming (partitioned, ordered, replayable)taps, rider-tapsHigh volume, ordering per key, and the ability to replay for re-rating and disaster recovery (ADR-0003).
Publish/subscribe domain eventsdomain-eventsContexts react to each other's facts without knowing who is listening. Adding a consumer (e.g. Apportionment in Phase 4) needs no change to the producer.
Transactional outboxEvery context that publishesState change and event publication succeed or fail together.
Request/response (REST)Apps and portals → APIs; DHS checks; Northgate verifications; Vantor fleet APIUsers and some partners need an immediate answer. Never used between contexts on the tap path.
Batch file transfer (SFTP)Northgate charges and settlement; one partner's statements; RiverCard extractsThe counterparties' standard for high-volume financial exchange, with clear cut-offs and audit trails.
WebhooksNorthgate charge results and chargebacks; CornerPay cash loadsThe external party pushes events as they happen. Always backed by a pull API for missed callbacks.
CDN pullDeny lists and validator configuration5,200 devices polling a static, signed file scales cheaply and works through Front Door caching.
Anti-corruption layerAll external systemsKeeps Northgate, Vantor, DHS, CornerPay and Castellan models out of Tapline's domain. Each can be replaced by rewriting one adapter (NFR-PORT-01).
ConformistCRT ERPTapline adopts the ERP's chart of accounts and journal format. Translating it would add cost with no benefit.

Deliberately not used

  • Shared databases between contexts. Each context owns its data (Data Architecture §2).
  • Distributed transactions (2PC). Replaced by outbox, idempotent consumers and compensating ledger entries.
  • Synchronous call chains on the tap path. A tap must be acceptable and storable with every downstream service down.

5. Error Handling & Retry Strategy

SituationBehavior
Transient failure calling a dependency (timeout, 5xx, throttling)Retry with exponential backoff and jitter using Microsoft.Extensions.Http.Resilience standard pipelines: 3 attempts for user-facing calls, longer schedules for background work. A circuit breaker opens after 50% failures over 30 s.
Consumer cannot process an event (bug or bad data)After 5 attempts the event moves to a parking stream (<stream>-parked) with the error attached, and the consumer continues. A parked event raises an alert and is never discarded.
Fixing parked eventsThe tapline-replay CLI re-publishes parked events (or a time range from the archive) after the fix. Idempotent consumers make replay safe.
Duplicate deliveryIgnored by unique ID at every consumer (tap_id, CloudEvents id, source_event_id).
Out-of-order delivery across partitionsAllowed. Within a rider key, order is guaranteed by partitioning; the Fare Engine re-rates anything that arrives late.
External callback missed (Northgate, CornerPay)Every webhook has a matching pull API. Reconciliation jobs pull anything not received by a cut-off time.
External system downRequests queue (Service Bus) with time-to-live per use case. Riders see "pending" rather than an error, e.g. a pending DHS check.
Money mismatchNever retried or corrected automatically. It becomes a reconciliation exception for Revenue Operations (UC-06).

6. Versioning Strategy

  • Events: schemas evolve backward-compatibly only. Optional fields may be added; nothing is removed, renamed or re-typed. The schema registry enforces this on publish. A breaking change creates .v2. The producer publishes both versions until every consumer has moved, for at least 90 days, then retires .v1 through the ARB.
  • Internal APIs: URI major version (/v1/). Additive changes don't change the version.
  • External APIs (Rider, Partner): same rule, with the deprecation periods in the API Specification Guide §3.
  • External interfaces we consume: versions and change notice are fixed in each ICD (e.g. 90 days' notice for breaking changes from Northgate).
  • Contract tests: each consumer's expectations of an event or API are tested in CI against the producer's published schema, so a producer can't merge a change that breaks a known consumer.
