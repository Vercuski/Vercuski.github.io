Solution Architecture Document — Project Tapline

Tapline in one paragraph

Tapline is an account-based fare system. Whatever a rider taps is only an identifier. Offline-capable validators decide accept or deny locally in under 300 ms and forward every signed tap to Azure. There, an event-streaming pipeline built on .NET 10 groups taps into trips, applies transfers and caps, and records every cent in an append-only ledger. Card data never enters CRT systems: P2PE readers encrypt it for Northgate Payments, which charges each card once a night. The design is organized around eight bounded contexts and is built to survive network loss at the edge, region loss in the cloud, and late or duplicated data everywhere.

1. Introduction

1.1 Purpose

This is the umbrella architecture document for Project Tapline. It connects the detailed architecture documents with a short narrative and records the architecture as approved at the end of Phase 0 design (ARB, 7 October 2026). It is the starting point for engineers joining the program, for the Gate 0 review, and for auditors.

1.2 Scope

Covers the whole Tapline system as defined in the Architecture Vision §5: validators and handhelds, cloud services, rider and staff channels, and integrations with Northgate, Vantor, State DHS, CornerPay, CRT ERP and RiverCard. Phase 4 capabilities (apportionment, partner portal, Keel Mobility) are included at container level but not yet designed in detail.

2. Executive Summary

RiverCard reaches end of support on 31 Dec 2028. Tapline replaces it with a system CRT owns, built on four architectural choices:

  1. Account-based, not card-based (ADR-0002). Fare logic lives in the cloud, so fare capping, reduced fares, open payments and regional integration all become configuration rather than card programming.
  2. Offline-first at the edge (ADR-0004). Validators never wait for the network. They decide from a signed local deny list and store taps until the cloud confirms receipt. Boarding speed and fare collection survive any outage up to 72 hours.
  3. Events as the source of truth (ADR-0003, ADR-0006). Taps are immutable facts in Event Hubs and an immutable archive. Trips, fares and ledger entries are derived from them deterministically, so late data is re-rated, duplicates are harmless, and a lost database can be rebuilt.
  4. No card data (ADR-0005). P2PE readers and Northgate tokens keep card numbers out of every CRT system, which keeps the PCI scope small.

The system is eight bounded contexts deployed as about fifteen services on AKS, with Azure SQL, Event Hubs and Fabric for data. It is designed for 12,000 taps a minute against a normal peak of about 1,100. The biggest technical risks are Journey DB write throughput, the team's limited experience with event streaming, and dependence on Vantor's firmware for edge behavior (§8).

4. Architectural Views

4.1 Context View

Tapline serves riders, inspectors, CRT staff and partner operators, and depends on Northgate, Vantor Fleet Cloud, State DHS, CornerPay, CRT ERP, CRT Scheduling and, until 2028, RiverCard. Validators are inside the system boundary: they are CRT assets running CRT configuration. See the Context Diagram.

4.2 Logical / Container View

Eight bounded contexts (Fare Policy, Journey, Rider Account, Media & Tokens, Eligibility, Payments & Settlement, Apportionment, Device Fleet) are deployed as services grouped by context (ADR-0007). The critical path is Validator → Device Gateway → taps → Tap Router → rider-taps → Fare Engine → domain-events → Ledger Service. The two-stream design gives one writer per rider key without distributed locks. Everything between contexts is asynchronous, so a failing context never stops taps being accepted. See the Container Diagram and the logical view in 4+1 Views §1.

4.3 Component View

The Fare Engine is the only container drawn at component level. Its core (Trip Builder, Fare Calculator, Cap Accumulator, Service-Day Clock) is pure and deterministic, and normal rating is just re-rating from the end of the timeline. See the Component Diagram.

4.4 Process View

Three runtime models: always-on validators; a streaming pipeline ordered per rider key; and a nightly chain from 03:00 to 06:00 that builds charges, settles with Northgate and posts to the ERP. Back-pressure stays in Event Hubs and never reaches validators. See Sequence Diagrams and 4+1 Views §2.

4.5 Deployment View

Azure East US 2 is primary, with a warm standby in Central US. Two AKS clusters (main zone and card-data zone) run across three availability zones each. Validators connect over a carrier private APN and ExpressRoute; handhelds and riders come in through Front Door. See Deployment Topology and 4+1 Views §4.

4.6 Data View

One database per context, no cross-database foreign keys, money in integer cents, and taps as immutable facts. The ledger uses Azure SQL ledger tables and achieves RPO 0 by replaying synchronously replicated events. Identity and travel are joined only by the media token, and that join is cut for analytics by monthly-rotated pseudonyms. See Data Architecture and Domain Model.

Guidance: If your stakeholders are more familiar with Kruchten's model than C4, 4plus1-views.md is an alternative (or complementary) way to organize this section.

6. Cross-Cutting Concerns

  • Security: zero trust between services (managed identities, mutual TLS inside clusters), a separate card-data zone, two-person controls for refunds and fare rules, and signed taps and deny lists. See Security Architecture and Threat Model.
  • Logging / Observability: OpenTelemetry everywhere, with every tap's tap_id used as a correlation ID end to end. Restricted data is excluded from logs by allow-listed structured fields. SLOs come from the NFRs. See Observability Strategy.
  • Error handling:
    • Streams: retry with backoff, then dead-letter to a parking stream with an alert. Nothing is silently dropped, and every parked message has a replay tool.
    • APIs: RFC 9457 problem details, with stable error codes per context (API Specification Guide).
    • Money: never auto-corrected. Differences become exceptions for Revenue Operations.
  • Idempotency: a system-wide rule. Every message carries a unique ID, and every consumer is idempotent by that ID (tap_id, source_event_id, deterministic charge IDs).
  • Time: all instants are stored in UTC. Local time is used only to derive service days and fare weeks, through the Service-Day Clock. Validators are GPS-synced.
  • Configuration management: fare rules are business data in the Fare Policy context, not configuration. Service configuration uses Azure App Configuration with feature flags. Validator configuration is versioned in tapline-edge and rolled out in rings.
  • Internationalization: all rider-facing text in English, Spanish, Vietnamese and Simplified Chinese through .NET resource files and a translation workflow. Currency is USD only.
  • Accessibility: WCAG 2.2 AA for every web and app screen, with automated checks in CI and manual testing with the Accessibility Advisory Committee before each release.
