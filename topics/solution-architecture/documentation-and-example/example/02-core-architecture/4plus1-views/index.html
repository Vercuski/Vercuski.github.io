4+1 View Model — Project Tapline

Why both C4 and 4+1

The C4 diagrams answer "what are the boxes?" for everyone. This document answers the questions engineers and operators keep asking that C4 doesn't: what runs concurrently and in what order (process view), how the code is laid out (development view), and what runs where (physical view). The five scenarios at the end check that the four views agree with each other.

1. Logical View

Audience: developers, designers.

The logical view is the aggregates and services of the Domain Model, arranged by bounded context. This class diagram shows the key abstractions and the main operations on them. It is not a database model; for that, see the Data Architecture.

Loading diagram…

Key abstractions shared across contexts live in a small Tapline.SharedKernel package: Money (integer cents plus currency, with no floating point anywhere), MediaToken, RiderKey, OperatorCode and the event envelope. Nothing else is shared. Contexts integrate through events and APIs, not shared classes.

2. Process View

Audience: integrators, performance engineers.

Tapline has three kinds of runtime process with very different behavior:

ProcessRunsConcurrency modelOrdering guarantee
Validator softwareContinuously on ~5,200 devicesSingle process per device: a reader thread, an upload thread and a deny-list threadTaps signed and stored in device order; the upload thread never deletes before acknowledgement
Streaming pipeline: Device Gateway → Tap Router → Fare Engine → Ledger ServiceContinuously in the cloudStateless gateway pods; Tap Router and Fare Engine own Event Hubs partitions; one writer per rider keyPer media token in taps; per rider key in rider-taps; none across riders, and none needed
Scheduled jobs: Settlement, deny-list full build, de-identification, GL post, apportionmentNightly windowsOne active instance per job (leader election through a Blob lease)Fixed chain, below
Request/response APIs: Account, Payments, Fare Policy, Device ManagementOn demandStateless pods behind API Management; scale on CPU and requestsPer request; writes use optimistic concurrency

Nightly chain (times are local):

Loading diagram…

Back-pressure and surge behavior. If the Fare Engine falls behind, for example during the stadium surge in NFR-SCALE-01, taps simply wait in rider-taps, which holds 7 days. Nothing upstream slows down: validators and the Device Gateway only need Event Hubs to accept writes. The Fare Engine scales out on consumer lag (KEDA on AKS) up to one instance per partition. Lag is the main operational metric for this pipeline.

3. Development View

Audience: developers, project management.

Code is split into four repositories by lifecycle, not by team:

tapline-platform/              .NET 10 solution: all CRT-built cloud services
├── src/
│   ├── SharedKernel/          Money, MediaToken, RiderKey, event envelope
│   ├── Journey/               Domain, Application, Infrastructure, Worker (Fare Engine, Tap Router)
│   ├── FarePolicy/            Domain, Application, Infrastructure, Api
│   ├── Accounts/              Modules: RiderAccount, Media, Eligibility; one Api host
│   ├── Payments/              Domain, Application, Infrastructure, Api, SettlementJobs
│   ├── Ledger/                Domain, Infrastructure, Worker, Api
│   ├── DeviceFleet/           DeviceGateway, DenyList, DeviceManagement
│   ├── Integration/           Adapters: Dhs, CornerPay, Erp, Partners
│   ├── Apportionment/         Phase 4
│   └── Contracts/             Event schemas (JSON Schema) and generated C# types
├── tests/                     Unit, property-based, contract, architecture tests per context
└── build/                     Directory.Build.props, analyzers, shared CI templates
tapline-apps/                  .NET MAUI Rider App and Inspection App; Blazor portals
tapline-edge/                  Validator configuration, deny-list format, Vantor integration test kit
tapline-infra/                 Bicep modules and environment definitions
  • Layering inside each context follows Onion / Clean Architecture: Domain depends on nothing; Application depends on Domain; Infrastructure and the host projects depend inward. An architecture test (NetArchTest) fails the build if a dependency points outward or if one context references another context's internals.
  • Contexts talk through Contracts only. Event types are generated from JSON Schema in Contracts/. A context may reference Contracts and SharedKernel, nothing else from another context.
  • Build and release: GitHub Actions. Each context builds and deploys independently (path filters), producing one container image per host. Promotion is dev → test → hardware lab → staging → production, with production deployment gated on the hardware-lab regression suite. Details are in Deployment Topology and IaC Notes.
  • Code standards: Coding Standards.

5. Scenarios (+1)

A handful of key use cases that exercise all four views: the glue and validation.

ScenarioViews ExercisedNotes
S1. Rider taps a bank card and reaches the daily cap (UC-01, UC-02)Logical, Process, PhysicalRiderFareWeek.Apply (logical) runs in the Fare Engine instance that owns the rider's partition (process), on the main-zone AKS cluster, fed by a validator over the private APN (physical). Checks: cap invariant inside one aggregate; single writer per rider key.
S2. Stadium surge with 120 buses reconnecting at once (NFR-SCALE-01)Process, PhysicalGateway pods scale on requests; rider-taps lag grows, then KEDA scales the Fare Engine to 32 instances; Journey DB write rate is the limit. Checks: no back-pressure reaches validators.
S3. A bus offline for two days uploads its taps (NFR-INTEG-01)Logical, ProcessLate taps are re-rated through the same code path; FareAdjusted carries differences only; the nightly chain nets adjustments into the next charge. Checks: determinism of the pure components.
S4. Azure East US 2 fails at the morning peak (NFR-AVAIL-07)Physical, ProcessValidators hold taps; failover to Central US; the Ledger Service replays 15 minutes of events and skips duplicates by source_event_id. Checks: RPO 0 by recomputation (see Data Architecture §5).
S5. Fare Policy publishes a new fare table for 1 July (US-05)Logical, Development, ProcessChange is data, not code: FareRuleVersion approved in the Policy context and published as an event; the Fare Engine's resolver cache picks it up; no deployment. Checks: the Contracts boundary and the absence of any code release.
